Çfarë bëjmë me SQL?

SELECTLexon të dhënat.
INSERTShton një rresht.
UPDATENdryshon rreshta.
DELETEHeq rreshta.

Ky lexim kërkon vetëm aktivitetin me ID 7. Ai kthen kolonat e zgjedhura dhe nuk ndryshon databazën.

SELECT id, title, seats_available
FROM activities
WHERE id = 7;

WHERE përcakton cilët rreshta preken. Pa të, një UPDATE ose DELETE mund të prekë shumë rreshta. “Nuk u gjet” nuk është e njëjta gjë me “databaza nuk u lidh”.

Java 10 · 9 / 32

Një lexim konkret në serverin e Next.js

Për tabelën ilustruese activities, funksioni i serverit lexon një aktivitet ose kthen null. ID-ja dhe lejet kontrollohen para thirrjes; leximi nuk ndryshon të dhënat.

import 'server-only';
import { neon } from '@neondatabase/serverless';
const sql = neon(process.env.DATABASE_URL!);
export async function readActivity(activityId: number) {
  const rows = await sql`SELECT id, seats_available
    FROM activities WHERE id = ${activityId}`;
  return rows[0] ?? null;
}

DATABASE_URL mbetet në server, pa prefiksin NEXT_PUBLIC_. Forma sql`… ${activityId}` dërgon vlerën si parametër; mos ndërto SQL duke bashkuar tekstin e përdoruesit.

Transaksioni: të gjitha ndryshimet ose asnjëri

Një konfirmim mund të kërkojë dy shkrime: regjistrimin e rezervimit dhe uljen e vendeve të lira.

BEGINMe Neon/HTTP: sql.transaction(…).
ShkrimetRuaj rezervimin dhe ndrysho vendet me kushtin përkatës.
COMMIT / ROLLBACKKonfirmo të gjitha ose anulo të gjitha.

Transaksioni shmang një rezervim të ruajtur pa ndryshimin përkatës të vendeve. Ai nuk e shpik vetë rregullin “vetëm një herë”: duhen kushtet dhe kufizimet e sakta.

Dy kërkesa lexojnë “1 vend”. A mjafton një if në JavaScript që të mos shitet dy herë?

Zbulo përgjigjen

Jo. Vendimi duhet të mbrohet edhe gjatë shkrimit në PostgreSQL, me kusht ose bllokim të përshtatshëm dhe transaksion kur ka disa ndryshime. Me Neon/HTTP përdor API-në e transaksionit; jo BEGIN dhe COMMIT në kërkesa HTTP të ndara.

Polling: ekrani pyet periodikisht

B pyet serverin: “A ka gjendje të re?” Le ta ndjekim një shitje bilete.

0 s
B lexon: 22 s
A shet: mbetet 15 s
B lexon: 110 s
B kontrollon sërish

Nëse shitja bëhet në sekondën 2, sa pret ekrani B në këtë shembull?

Zbulo përgjigjen

Rreth 3 sekonda, plus rrjetin dhe serverin. B tregon 2 deri te leximi në sekondën 5.

Polling është përditësim afër kohës reale. Intervali 5 sekonda nuk është premtim për dorëzim të menjëhershëm.

EkraniHap një lidhje EventSource.

SSE (Server-Sent Events – ngjarje të dërguara nga serveri) përcjell të dhëna në drejtimin server–klient. Komandat e përdoruesit mund të mbeten kërkesa HTTP të veçanta.

Duhet menduar rilidhja, ngjarjet e humbura dhe kufijtë e mjedisit ku e publikojmë serverin.

Përditësimi ka ritëm dhe kosto

Dy ekrane që lexojnë çdo 5 sekonda bëjnë afërsisht 24 kërkesa leximi në minutë, pa përfshirë veprimet.

  • Planifiko leximin tjetër pasi të mbarojë i tanishmi.
  • Ndalo timer-in kur largohet komponenti. Pauzo kur faqja fshihet.
  • Kur dështon rrjeti, prit më gjatë para provës tjetër. Kur faqja aktivizohet, lexo menjëherë.

Ky është ritmi i ushtrimit me dy përdorues testimi. Për një aplikacion me shumë përdorues, krahasojmë koston dhe vonesën e mekanizmave.
